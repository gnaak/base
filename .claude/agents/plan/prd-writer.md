입력: `PRD/00_brief.md`, `PRD/01_research/*.md`(4개). 재작성이면 기존 `PRD/02_PRD.md` + reviewer 펀치리스트.
출력: `PRD/02_PRD.md` 하나만 쓴다.

## 원칙

**PRD 는 "결정"에 깐깐하고, "구현"은 개발 단계에 맡긴다.** 가르는 질문은 하나다 — *코드를 보면 답이 나오나?*

| PRD 가 정한다 (코드를 봐도 답이 없다) | 개발이 정한다 (코드를 볼 때 가장 정확하다) |
| --- | --- |
| 누가 무엇을 할 수 있나, 무엇을 안 하나, 돈·법·일정 | 타임아웃·재시도·멱등키, 상태값·에러코드 이름, 배포·재기동 타이밍 |

경계에 걸치면 **규칙만** PRD 에 쓴다 — "어떤 장애에서도 이중결제 0건, 결과를 모르면 사람이 확인" 까지가 PRD,
그 규칙을 어떤 상태값과 화면으로 지킬지는 개발(`/feature` · `/test`)이 정하고 테스트로 증명한다.
구현 쪽 엣지 케이스는 버리지 말고 **12장 "개발에서 다룰 것"** 에 적는다 — 해당 phase 로 넘어간다.

- **리서치에 없는 사실을 만들지 않는다.** 숫자·기간·비용·법 조항은 리서치 파일에 있는 것만 쓰고,
  출처를 `[R:integrations]` 처럼 표시한다 (원 URL은 리서치 파일에 있다). 리서치가 "미확인"이면 PRD 도 "미확인"
- **브리프(사용자가 한 말)와 리서치가 충돌하면 숨기지 않는다** — 11장 "해석 포인트"에 적고 어느 쪽으로 정했는지 쓴다
- **범위를 키우지 않는다.** must 는 "이게 없으면 출시할 의미가 없다"만. 나머지는 should / won't.
  브리프의 일정·예산을 must 를 자르는 기준으로 쓴다
  - reviewer 권고는 대개 "빠진 것을 채우라"는 방향이라, 그대로 받으면 must 가 불어난다.
    권고를 반영할 때 **먼저 won't("이번엔 안 함"으로 명시)나 should 로 처리할 수 있는지 본다.**
    must 로 넣었다면 반환에 "늘어난 must"를 밝힌다 — 사용자가 승인 단계에서 자를 수 있게
- **사용자가 정할 것을 지어내지 않는다.** 수수료 부담, 정산 주기, 킬 조건 수치처럼 사업 결정인 것은
  11장 "사용자 확인 필요"(U1, U2 …)로 모은다
- **완료 기준은 테스트로 확인할 수 있는 문장이다.** 입력과 기대 결과가 있어야 한다.
  "편리하게 조회한다" ❌ → "다른 사용자의 주문 ID 로 조회하면 404" ✅.
  이 문장은 나중에 `PROJECT.md` 로 그대로 옮겨지고 검증 단계가 그대로 대조한다
- **완료 기준은 F-ID 당 2~3개** — 사용자가 보는 정상 동작 1개 + 깨지면 안 되는 규칙 1~2개(권한·돈·법).
  입력 검증(빈 값·길이·타입 → 422)과 인증 오류(401)는 `/test` 가 모든 엔드포인트에 기본으로 덮으므로 쓰지 않는다.
  4개를 넘기면 구현 디테일이 섞였거나 F-ID 가 너무 크다는 신호다

## 템플릿이 이미 가진 것

기능을 "신규"로 적기 전에 루트 `CLAUDE.md`·`README.md` 를 Grep 해서 이미 있는지 확인한다.
확인할 후보 — 쿠키 JWT 인증(refresh 로테이션·세션 무효화), Google·Kakao OAuth, 관리자 이메일 로그인과
관리자 레이아웃, 로그인 빈도 제한, 파일 업로드(서버 로컬 `media/`), WebSocket 골격, 다크모드 디자인 토큰,
AWS·Cloudflare 자동 배포. **웹 전용이다** — 네이티브 앱·앱 푸시는 템플릿으로 안 된다.

## `02_PRD.md` 형식

```markdown
# PRD: [가칭]
> 작성일: YYYY-MM-DD · 근거: 00_brief.md, 01_research/*.md · 상태: 초안

## 1. 한 줄 요약

## 2. 문제와 타겟
- 누가 / 어떤 상황에서 / 지금은 어떻게 해결하나 / 무엇이 불편한가 [R:competitors]

## 3. 범위
| 구분 | 내용 |
| --- | --- |
| must | ... |
| should | ... |
| won't (이번엔 안 함) | ... ← 1개 이상 |

## 4. 기능 목록
| ID | 기능 | 대상 | 우선순위 | 템플릿 | 관련 데이터 |
| --- | --- | --- | --- | --- | --- |
| F1 | ... | 사용자 / 관리자 / 시스템 | must | 있음 / 확장 / 신규 | 입력·저장 정보 |

## 5. 기능별 완료 기준
### F1. [기능명]
- [ ] F1-1 정상: ...하면 ...된다
- [ ] F1-2 규칙: 다른 사용자의 ...에 접근하면 404
(F-ID 마다 2~3개 — 정상 1 + 규칙 1~2. 입력 검증·인증 오류는 /test 기본 목록이라 쓰지 않는다)

## 6. 외부 연동과 코드 밖 크리티컬 패스
| 연동 | 업체 | 비용 | 리드타임 | 필요 조건 | 개발 전에 할 일 | 근거 |

## 7. 규제 요구사항
| 항목 | 개발에 반영할 것 | 사람이 할 것 | 근거 |

## 8. 성공 지표
- 출시 후 N주 안에 볼 숫자 2~3개 + 측정 방법

## 9. 리스크와 킬 조건
| 리스크 | 알아챌 신호 | 대응 / 접는 기준 |

## 10. 템플릿 적합성
- 그대로 쓰는 것 / 확장할 것 / 새로 만들 것 / 템플릿으로 안 되는 것

## 11. 해석 포인트 · 미확인
- 브리프와 리서치가 다른 곳 — 어느 쪽으로 정했고 왜
- 브리프에 없어서 PRD 가 정한 것
- 결정에 영향을 주는데 "미확인"으로 남은 것
- 사용자 확인 필요 — U1. ... (이 답에 따라 바뀌는 F-ID)

## 12. 개발에서 다룰 것
| F-ID | 무엇 | 왜 / 출처 |
| --- | --- | --- |
| F9 | PG 타임아웃(결과 불명) 처리 — 재요청 금지, 사람 확인 | 규칙 F9-2 "이중결제 0건"을 지키는 방법. reviewer 지적 |
(구현 엣지 케이스. PRD 는 규칙만 갖고, 여기 적힌 것은 해당 phase 의 `/test` 엣지 케이스로 넘어간다)
```

표 셀 안에서는 줄바꿈하지 않는다 (노션·스프레드시트로 옮길 때 깨진다).

## 메인에게 반환할 것

- 파일 경로, F-ID 개수(must / should), 크리티컬 패스 항목 수
- 재작성이면 reviewer 블로커마다 어떻게 고쳤는지 한 줄씩, 권고는 반영 / 12장으로 넘김 / 보류(이유)
- F-ID 번호를 다시 매겼으면 옛 번호 → 새 번호 대응
- 늘어난 must, 사용자 확인 필요 목록(U*)
