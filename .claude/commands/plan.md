$ARGUMENTS

`$ARGUMENTS` 의 아이디어로 새 프로젝트를 기획한다. 결과물은 `PRD/` 폴더와 `PROJECT.md` · `PROGRESS.md` · `DECISIONS.md` 다.
**코드는 한 줄도 쓰지 않는다** — 개발은 `PROJECT.md` 의 phase 1 부터 `/feature` · `/fullstack` 으로 한다.

**무인으로 돈다.** 사람이 붙는 곳은 처음 인터뷰뿐이고, 그 뒤로는 묻지도 기다리지도 않는다.
기준은 하나 — **되돌리기 쉬운 결정은 기본값으로 진행하고, 되돌리기 어려운 결정(돈·법·범위)은 기본값으로 진행하되
`DECISIONS.md` 에 올려 사람이 나중에 바꾸게 한다.** 개발은 그런 결정을 설정값으로 구현해서, 바꾸는 일이 값 하나가 되게 한다.

```
PRD/
  00_brief.md                ← 사용자가 한 말 + 인터뷰 답
  01_research/
    competitors.md · ux.md · design.md · integrations.md · regulations.md
  02_PRD.md                  ← 범위 · 기능 · 기능별 완료 기준 · 크리티컬 패스 · 리스크 · U*(기본값 포함)
  03_PAGE.md                 ← 화면 목록 · 라우트 · 대상 · 포함 F-ID · 흐름 · 필요한 UI 패턴
  04_DESIGN.md               ← 고객 화면 테마 전부(토큰 라이트·다크) · 기본 테마 · 만들 컴포넌트
PROJECT.md · PROGRESS.md     ← phase 계획
DECISIONS.md                 ← 사람이 아침에 보는 페이지의 원본 — 결정 필요 · 사람이 할 일 · 막힌 곳
```

## 0. 시작 전

- `$ARGUMENTS` 가 비어 있으면 "무엇을 만들고 싶은지" 한두 줄을 먼저 묻는다
- `PRD/` 나 `PROJECT.md` 가 이미 있으면 **새로 할지 / 이어갈지** 묻는다. 이어가면 없는 파일부터
- 오늘 날짜를 확인해 둔다 — 리서치의 확인일에 쓴다

## 1. 인터뷰 — 유일하게 사람이 붙는 곳

서브에이전트는 사용자에게 물을 수 없다. **물어볼 것은 여기서 다 묻는다.**
AskUserQuestion 으로 최대 2라운드, 라운드당 4개까지. 아이디어 문장에 이미 답이 있으면 묻지 않는다.
사용자가 "그냥 돌려"처럼 답하지 않겠다고 하면 인터뷰를 건너뛰고 전부 "모름"으로 적는다.

**1라운드 (항상)**

| 질문 | 왜 필요한가 |
| --- | --- |
| 누가 쓰나 (타겟·예상 규모) | 경쟁·UX·디자인 리서치의 범위 |
| 지금은 이 문제를 어떻게 해결하고 있나 | 진짜 경쟁자는 대체재(엑셀·전화·카톡)인 경우가 많다 |
| 돈은 어떻게 버나 (구독·수수료·광고·내부용) | 결제 연동 여부 → PG 심사 → 일정 |
| 언제까지, 몇 명이서 | must 를 자르는 기준 |

**2라운드 (필요할 때만)**

| 질문 | 왜 필요한가 |
| --- | --- |
| 로그인 방식 (Google·Kakao·이메일·없음) | 템플릿 기본은 Google·Kakao OAuth + 관리자 이메일 로그인 |
| 관리자 화면이 필요한가 | 관리자 레이아웃은 이미 있다 |
| 개인정보·결제·위치·의료·금융·청소년 중 해당하는 것 | 규제 리서치의 깊이 |
| 참고하는 서비스가 있나 (기능이든 분위기든) | 경쟁·디자인 리서치의 출발점 |

"모르겠다"는 답은 그대로 적고 리서치에 넘긴다. **추측으로 채우지 말 것.**
인터뷰가 끝나면 "이제부터 사람 없이 끝까지 돕니다. 결과는 DECISIONS.md 에 모읍니다" 라고 알리고 넘어간다.

## 2. 브리프 — `PRD/00_brief.md`

```markdown
# 브리프: [가칭]
> 작성일: YYYY-MM-DD

## 원문
(사용자가 한 말 그대로)

## 인터뷰
- Q: ... — A: ...

## 리서치에 넘길 질문
- competitors: ...
- ux: ...
- design: ...
- integrations: ...
- regulations: ...
```

## 3. 리서치 — `plan-researcher` 5개를 **한 메시지에서 병렬로**

호출마다 프롬프트에 넣는 것: 주제(`competitors` · `ux` · `design` · `integrations` · `regulations`),
브리프 경로, 출력 파일 `PRD/01_research/{주제}.md`, 오늘 날짜, 그 주제의 질문.

끝나면 5개 파일이 다 있는지, 출처 목록이 비어 있지 않은지 확인한다. **실패한 주제만** 다시 부른다 (한 번).
그래도 실패하면 그 주제 없이 진행하고 `DECISIONS.md` "막힌 곳"에 적는다.

## 4. PRD — `prd-writer` → `prd-reviewer`

1. `prd-writer` 호출 → `PRD/02_PRD.md`
2. `prd-reviewer` 호출. ❌ 블로커가 있으면 펀치리스트를 그대로 `prd-writer` 에 넘겨 다시 쓰게 한다
3. **재작성은 최대 2회.** 그래도 블로커가 남으면 멈추지 않는다 — 상태를 `블로커 남음` 으로 두고,
   남은 블로커를 `DECISIONS.md` "막힌 곳"에 그대로 옮긴 뒤 다음 단계로 간다

메인이 reviewer 를 건너뛰고 통과시키지 않는다. ⚠️ 권고는 반영하거나, 반영하지 않은 이유를 `DECISIONS.md` 에 적는다.
(이 규칙은 5단계의 페이지 맵·디자인 문서에도 똑같이 적용된다)

통과하면 `02_PRD.md` 상태를 `자동 승인` 으로 바꾼다. **U\* 는 묻지 않는다** — PRD 11장의 기본값으로 진행하고 6단계에서 `DECISIONS.md` 로 옮긴다.

## 5. 페이지 맵 → 디자인 — `page-mapper` → `design-writer`

순서대로 (디자인이 페이지의 UI 패턴을 보고 컴포넌트를 정하므로):

1. `page-mapper` → `PRD/03_PAGE.md` → `prd-reviewer`(대상: `03_PAGE.md`) → 블로커면 재작성 (최대 2회)
2. `design-writer` → `PRD/04_DESIGN.md` → `prd-reviewer`(대상: `04_DESIGN.md`) → 블로커면 재작성 (최대 2회)

메인이 직접 센다: must F-ID 가 전부 `03_PAGE.md` 1장이나 4장에 있는지.

**디자인 방향은 묻지 않는다.** 후보를 전부 테마로 저장하고 design-writer 가 기본 테마를 근거와 함께 고른다.
사람은 실제 화면이 나온 뒤 `data-theme` 값만 바꿔 보며 고른다.
페이지 맵·디자인이 PRD 에 없는 것을 찾았으면(반려 후 재신청 경로, 사진 데이터 없음 등) `DECISIONS.md` 에 적는다.
그게 must 를 늘려야 하는 거라면 must 를 늘리지 말고 "범위 결정 필요"로 올린다 — 범위는 사람이 정한다.

## 6. `PROJECT.md` · `PROGRESS.md` · `DECISIONS.md`

### `PROJECT.md` — 루트 `CLAUDE.md` "phase 관리" 양식

- **phase 0 "준비"** 를 맨 앞에 둔다 — PRD 6장 크리티컬 패스와 7장 "사람이 할 것"(사업자·심사 신청·약관 등).
  개발 phase 가 아니라 사람이 할 일 목록이다. 무인 개발은 phase 0 을 건너뛰고 테스트 키로 진행한다
- **phase 1 "디자인 기반"** 을 개발 맨 앞에 둔다 — `04_DESIGN.md` 를 실제로 적용한다:
  `DESIGN.md` 에 고객 화면 절 추가, `index.css` 에 **테마 전부**(`.theme-client[data-theme="x"]` · `.dark .theme-client[data-theme="x"]`),
  신규 토큰의 `tailwind.config.js` 클래스, 고객 레이아웃 최상단에 `class="theme-client" data-theme="{기본}"`, 폰트 로딩,
  `04_DESIGN.md` 7장 중 여러 페이지가 쓰는 공통 컴포넌트. 완료 기준은 기능이 아니라 이것들이다 —
  "고객 화면에서 주 색이 기본 테마 값", "`data-theme` 만 바꾸면 다른 테마 값", "관리자 화면은 그대로", "다크모드에서 각 테마의 다크 값"
- phase 2 부터는 must 기능을 의존 순서로 묶는다 (데이터 모델·인증 → 핵심 기능 → 관리자 → 외부 연동 순이 흔하다).
  템플릿에 "있음"인 기능은 phase 로 만들지 않는다. 각 phase 에 **"페이지: P3, P5"** 를 단다 (`03_PAGE.md` P-ID)
- **U\* 가 걸린 phase 에는 "설정값: U1(수수료 비율), U4(마감 시각)" 줄을 단다** — 그 phase 는 해당 결정을
  하드코딩하지 않고 기본값을 가진 설정(`RawEnv` 필드 → 운영은 SSM)으로 구현한다. "구조" U 는 기본값 구조로 만든다
- 각 phase 의 **완료 기준은 `02_PRD.md` 5장의 문장을 ID 째로 그대로 옮긴다.** 새로 지어내지 말 것 —
  검증 단계가 이 문장을 그대로 대조한다 (`[R:…]` 출처 태그만 빼도 된다)
- **기준이 다른 phase 의 기능을 필요로 하면 그 기능이 생기는 phase 로 옮긴다** — 기준이 가리키는 F-ID 중
  가장 늦은 phase 에 둔다. ID 는 그대로 두고 옆에 `← F7` 처럼 이유를 단다.
  예: "휴대폰 번호 없이 구독(F7)하면 거부"(F1-2)는 F1 이 앞 phase 여도 F7 이 생기는 phase 에서야 테스트된다.
  옮긴 기준이 한 phase 에 몰리면 phase 순서를 다시 본다 (집계 화면처럼 읽기만 하는 기능은 앞으로 당기기 쉽다)
- 다 옮긴 뒤 **must 기준 개수가 PRD 와 같은지, 빠지거나 두 번 들어간 ID 가 없는지** 센다
- `02_PRD.md` **12장 "개발에서 다룰 것"** 은 그 F-ID 가 들어간 phase 의 "개발에서 다룰 것" 줄로 옮긴다.
  완료 기준이 아니라, 그 phase 의 `/test` 가 엣지 케이스로 덮을 목록이다
- 커밋 줄은 영역 접두사 형식 (`feat: ...`)

### `DECISIONS.md` — 사람이 아침에 볼 것

```markdown
# 결정 필요 — [가칭]
> 마지막 갱신: YYYY-MM-DD HH:MM · 단계: 기획 완료 (개발 전)

## 🔴 돈 · 법 · 범위 — 기본값으로 진행 중
| U | 질문 | 지금 기본값 | 다른 선택지 | 바꾸는 법 | 영향 |
| --- | --- | --- | --- | --- | --- |
| U1 | ... | ... | ... | 설정 `fee_rate` / 구조(개발 필요) | F14 · phase 5 |
("구조" 인 것을 맨 위에 — 늦게 바꿀수록 다시 만드는 양이 커진다)

## 🟡 확인 권장 — 되돌리기 쉬움
- 디자인 테마: 기본 b(정갈한 신뢰). 다른 후보 a·c — 고객 레이아웃 `data-theme` 값
- 페이지 맵·디자인이 찾은 PRD 공백: ...

## 🧑 사람이 할 일 — 리드타임 긴 순 (phase 0)
1. PG 빌링 심사 신청 — 최소 2~4주 — 전제: 사업자등록·통신판매업 신고

## ⛔ 막힌 곳
(리서치 실패, 해소 안 된 블로커. 개발 중에는 실패한 phase·테스트도 여기에 쌓인다)

## 🔍 검토 필요
(개발 중에 쌓인다 — 생성된 마이그레이션, 보안 검토 ❌, 완료 기준 미충족)
```

마지막 보고(사람이 있으면): 만든 파일 목록, phase 개수, `DECISIONS.md` 의 🔴 개수와 🧑 첫 항목.
다음은 **`/autopilot`** — phase 1 부터 사람 없이 끝까지 개발한다 (손으로 한 phase 씩 하려면 `/fullstack` · `/feature`).

## 하지 말 것

- 코드·마이그레이션·설정 파일을 고치지 말 것 (`DESIGN.md`·`index.css` 포함 — 적용은 phase 1). 이 커맨드는 기획만 한다
- 리서치에 없는 숫자(시장 규모·가격·심사 기간)를 메인이 보태지 말 것
- 되돌리기 어려운 결정(돈·법·범위)을 `DECISIONS.md` 에 올리지 않고 정하지 말 것
- must 를 늘려야 하는 발견을 혼자 must 에 넣지 말 것 — "범위 결정 필요"로 올린다
- 템플릿 저장소(base) 자체에 `PRD/` · `PROJECT.md` · `DECISIONS.md` 를 커밋하지 말 것 — 새 프로젝트에서 쓰는 것이다
