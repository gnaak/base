$ARGUMENTS

`$ARGUMENTS` 의 아이디어로 새 프로젝트를 기획한다. 결과물은 `PRD/` 폴더와 `PROJECT.md` · `PROGRESS.md` 다.
**코드는 한 줄도 쓰지 않는다** — 개발은 승인된 `PROJECT.md` 의 phase 1 부터 `/feature` · `/fullstack` 으로 한다.

```
PRD/
  00_brief.md                ← 사용자가 한 말 + 인터뷰 답
  01_research/
    competitors.md · ux.md · integrations.md · regulations.md
  02_PRD.md                  ← 범위 · 기능 · 기능별 완료 기준 · 크리티컬 패스 · 리스크
PROJECT.md · PROGRESS.md     ← 승인 후 생성
```

## 0. 시작 전

- `$ARGUMENTS` 가 비어 있으면 "무엇을 만들고 싶은지" 한두 줄을 먼저 묻는다
- `PRD/` 나 `PROJECT.md` 가 이미 있으면 **새로 할지 / 이어갈지** 묻는다. 이어가면 없는 파일부터
- 오늘 날짜를 확인해 둔다 — 리서치의 확인일에 쓴다

## 1. 인터뷰 — 메인 대화에서

서브에이전트는 사용자에게 물을 수 없다. **물어볼 것은 여기서 다 묻는다.**
AskUserQuestion 으로 최대 2라운드, 라운드당 4개까지. 아이디어 문장에 이미 답이 있으면 묻지 않는다.

**1라운드 (항상)**

| 질문 | 왜 필요한가 |
| --- | --- |
| 누가 쓰나 (타겟·예상 규모) | 경쟁·UX 리서치의 범위 |
| 지금은 이 문제를 어떻게 해결하고 있나 | 진짜 경쟁자는 대체재(엑셀·전화·카톡)인 경우가 많다 |
| 돈은 어떻게 버나 (구독·수수료·광고·내부용) | 결제 연동 여부 → PG 심사 → 일정 |
| 언제까지, 몇 명이서 | must 를 자르는 기준 |

**2라운드 (필요할 때만)**

| 질문 | 왜 필요한가 |
| --- | --- |
| 로그인 방식 (Google·Kakao·이메일·없음) | 템플릿 기본은 Google·Kakao OAuth + 관리자 이메일 로그인 |
| 관리자 화면이 필요한가 | 관리자 레이아웃은 이미 있다 |
| 개인정보·결제·위치·의료·금융·청소년 중 해당하는 것 | 규제 리서치의 깊이 |
| 참고하는 서비스가 있나 | 경쟁 리서치의 출발점 |

"모르겠다"는 답은 그대로 적고 리서치에 넘긴다. **추측으로 채우지 말 것.**

## 2. 브리프 — `PRD/00_brief.md`

```markdown
# 브리프: [가칭]
> 작성일: YYYY-MM-DD

## 원문
(사용자가 한 말 그대로)

## 인터뷰
- Q: ... — A: ...

## 리서치에 넘길 질문
- competitors: ...
- ux: ...
- integrations: ...
- regulations: ...
```

## 3. 리서치 — `plan-researcher` 4개를 **한 메시지에서 병렬로**

호출마다 프롬프트에 넣는 것: 주제(`competitors` · `ux` · `integrations` · `regulations`),
브리프 경로, 출력 파일 `PRD/01_research/{주제}.md`, 오늘 날짜, 그 주제의 질문.

끝나면 4개 파일이 다 있는지, 출처 목록이 비어 있지 않은지 확인한다. **실패한 주제만** 다시 부른다.

## 4. PRD — `prd-writer` → `prd-reviewer`

1. `prd-writer` 호출 → `PRD/02_PRD.md`
2. `prd-reviewer` 호출. ❌ 블로커가 있으면 펀치리스트를 그대로 `prd-writer` 에 넘겨 다시 쓰게 한다
3. **재작성은 최대 2회.** 그래도 블로커가 남으면 멈추고 사용자에게 상황을 보고한다

메인이 reviewer 를 건너뛰고 통과시키지 않는다. ⚠️ 권고는 반영하거나, 반영하지 않은 이유를 사용자 보고에 적는다.

## 5. 사용자 승인

보여줄 것 (리뷰 원문을 붙이지 말고 요약한다):

- 한 문단 요약 — 무엇을, 누구에게, 왜
- must 기능 목록 (F-ID)
- **코드 밖 크리티컬 패스** — 심사·승인·계약처럼 개발보다 먼저 시작해야 하는 것과 리드타임
- 리스크와 킬 조건
- 해석이 갈린 곳, 결정에 영향을 주는 "미확인" 항목
- 재작성 중 **늘어난 must** — 일정 대비 많으면 무엇을 should·won't 로 내릴지 제안한다

PRD 11장의 **"사용자 확인 필요"(U1, U2 …)는 AskUserQuestion 으로 실제로 묻는다.**
답을 `02_PRD.md` 에 반영하고(바뀐 F-ID 완료 기준 포함), 답을 미룬 항목은 `미정`으로 남겨 phase 0 에 올린다.

**승인 전에는 `PROJECT.md` 를 만들지 않는다.** 수정 요청이 오면 `02_PRD.md` 를 고치고
(범위가 바뀌었으면 reviewer 를 다시 거쳐) 다시 보여준다. 승인되면 `02_PRD.md` 의 상태를 `승인`으로 바꾼다.

## 6. `PROJECT.md` · `PROGRESS.md`

루트 `CLAUDE.md` "phase 관리" 양식으로 만든다.

- **phase 0 "준비"** 를 맨 앞에 둔다 — 6장 크리티컬 패스와 7장 "사람이 할 것"(사업자·심사 신청·약관 등).
  개발 phase 가 아니라 사람이 할 일 목록이다. 아직 `미정`인 U* 는 "답에 따라 바뀌는 phase" 와 함께 표로 둔다 —
  그 phase 를 시작하기 전에 답을 받아야 한다
- phase 1 부터는 must 기능을 의존 순서로 묶는다 (데이터 모델·인증 → 핵심 기능 → 관리자 → 외부 연동 순이 흔하다).
  템플릿에 "있음"인 기능은 phase 로 만들지 않는다
- 각 phase 의 **완료 기준은 `02_PRD.md` 5장의 문장을 ID 째로 그대로 옮긴다.** 새로 지어내지 말 것 —
  검증 단계가 이 문장을 그대로 대조한다 (`[R:…]` 출처 태그만 빼도 된다)
- **기준이 다른 phase 의 기능을 필요로 하면 그 기능이 생기는 phase 로 옮긴다** — 기준이 가리키는 F-ID 중
  가장 늦은 phase 에 둔다. ID 는 그대로 두고 옆에 `← F7` 처럼 이유를 단다.
  예: "휴대폰 번호 없이 구독(F7)하면 거부"(F1-2)는 F1 이 phase 1 이어도 F7 이 생기는 phase 에서야 테스트된다.
  옮긴 기준이 한 phase 에 몰리면 phase 순서를 다시 본다 (집계 화면처럼 읽기만 하는 기능은 앞으로 당기기 쉽다)
- 다 옮긴 뒤 **must 기준 개수가 PRD 와 같은지, 빠지거나 두 번 들어간 ID 가 없는지** 센다
- `02_PRD.md` **12장 "개발에서 다룰 것"** 은 그 F-ID 가 들어간 phase 의 "개발에서 다룰 것" 줄로 옮긴다.
  완료 기준이 아니라, 그 phase 의 `/test` 가 엣지 케이스로 덮을 목록이다
- 커밋 줄은 영역 접두사 형식 (`feat: ...`)
- `PROGRESS.md` 는 phase 마다 `⬜ 대기`

마지막 보고: 만든 파일 목록, phase 개수, **phase 0 의 사람 할 일**(리드타임 긴 순).

- 템플릿 저장소(base) 자체에 `PRD/` · `PROJECT.md` 를 커밋하지 말 것 — 새 프로젝트에서 쓰는 것이다
