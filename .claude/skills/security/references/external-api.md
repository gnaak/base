# 외부 연동 (결제 · 알림 · 웹훅)

목표: 돈이 두 번 나가지 않고, 가짜 웹훅으로 주문 상태가 바뀌지 않고, 업체 키가 새지 않는다.

## 어디를 보나

- `backend/app/module/infra/{업체}/` — 업체 클라이언트
- `backend/app/core/utils/http_client.py` 의 `request_json()` 호출부 — `retries`, `upstream_errors`, 504 처리
- 웹훅 라우터 (`*_webhook_router.py`)
- 비싼 외부 호출을 일으키는 우리 엔드포인트의 `rate_limit`

## 체크리스트

### 결과 불명 (이중 처리)
- [ ] 결제·취소·발송처럼 부작용이 있는 호출에서 **504 `UPSTREAM_TIMEOUT` 을 실패로 처리하지 않는다** —
      "확인 필요" 상태로 두고 업체 결과 조회로 확정한다. 실패로 보고 재결제하면 ❌ 이중결제
- [ ] 돈이 오가는 요청에 업체의 멱등키(Idempotency-Key)를 우리 쪽 고유값(주문·회차 ID)으로 붙인다
- [ ] 재시도가 "자동결제 배치를 다시 돌리기" 같은 우리 쪽 재실행에도 안전하다 — 같은 회차의 성공이 1건을 넘지 않게 DB 제약이나 상태 검사

### 웹훅
- [ ] **서명을 검증한다** (HMAC 등, 상수 시간 비교 `hmac.compare_digest`). 없으면 ❌ — 누구나 "결제 완료"를 보낼 수 있다
- [ ] 같은 이벤트가 두 번 와도 한 번만 반영된다 (이벤트 ID 저장)
- [ ] 웹훅의 금액·상태를 그대로 믿지 않고 우리 주문과 대조한다
- [ ] 서명 검증에 **원문 바디**를 쓴다 (파싱 후 다시 직렬화한 값이 아니다)

### 키·설정
- [ ] 업체 키는 `RawEnv` → `settings`. 코드·테스트에 실키 없음
- [ ] 운영에서 키가 없을 때 조용히 mock 으로 돌지 않는다 (503 으로 실패)
- [ ] 업체 응답 본문(`UpstreamError.body`)을 클라이언트에 그대로 주지 않는다

### 비용
- [ ] 결제 요청·알림 발송·AI 호출을 일으키는 엔드포인트에 `rate_limit` 이 있다 — 없으면 연타로 돈이 나간다 (❌ 유료 API 면)
- [ ] 업체의 429 에 `retries` 로 대응한다 (요청 폭주를 그대로 실패시키지 않게) — ⚠️
